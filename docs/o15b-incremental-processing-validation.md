## 設計審査時の条件

設計段階の判定は**条件付き合格（PASS WITH REQUIRED CORRECTIONS）**だった。

画面ごとに必要期間だけ返す方針と、変更された原本だけを正規化する方針は妥当である。ただし、次の3点を修正しない設計は不合格とする。

1. トップページを「直近7日だけ」にしない。現行画面には過去30日比較があるため、**直近7日の詳細と、当日を含む最低31睡眠日分の軽量要約**を返す。
2. 「変更ファイルが属する月だけ再構築」を正しさの境界にしない。**旧版と新版の影響範囲の和**から、睡眠日の18時境界、30分以内のブロック結合、重複ブロックの連結成分まで追跡して再構築する。月は配信・保存の区画として使う。
3. 期間指定APIだけを追加して完了としない。現行ローダーが全JSON/JSONLを読むままではサーバーI/Oは減らないため、**完成スナップショットID単位のメモリーキャッシュ、または再生成可能な期間索引**を併設する。

この条件は実装へ反映済みである。`npm test`（Processor、ローカルruntime、睡眠分析、Drive認証、Health集計、画面診断、印刷を含む全スイート）、`npm run build`、`npm run lint`を最終回帰ゲートとする。

## 合格する構成

### 1. 読み取り経路

```text
完成スナップショット
  → snapshotId単位の読取キャッシュ／期間索引
  → 画面別API
  → 必要時だけ画面データを更新
```

| 画面 | 取得内容 | 更新契機 |
| --- | --- | --- |
| トップ | 最新日の詳細、直近7日の詳細、当日を含む最低31睡眠日の軽量要約、同期間のHealth文脈 | 初回、`snapshotId`変更時 |
| タイムライン | 選択した睡眠月の正規化記録・出典情報、またはraw/unified両表示を再現できる月データ | 月変更、`snapshotId`変更時 |
| 分割睡眠 | タイムラインと同じ選択月データ | 月変更、`snapshotId`変更時 |
| 印刷 | 選択月データ | 印刷開始時 |
| 診断 | 診断・出典品質の事前集計値。必要なときだけ期間詳細 | 初回、`snapshotId`変更時 |
| 取り込み状況・設定 | 軽量なstatus、Drive同期状態、最新`snapshotId` | 60秒ポーリング可 |

毎分のポーリングは軽量statusだけにする。前回の`snapshotId`と同じなら睡眠データを再取得しない。画面遷移や月変更時は対象期間だけ取得する。

完成前の`.working`はキャッシュ対象にせず、`complete.json`を検証した完成スナップショットだけを公開する。キャッシュはsnapshotId変更時に一括で切り替え、旧キャッシュは進行中の要求が終わってから破棄する。

現行Processed Data Contractの完全なJSON/JSONLスナップショットは耐久・監査用として維持する。月別JSONやSQLiteを使う場合は、完成スナップショットから再生成できる読取索引とし、正本にしない。この構成なら既存の不変スナップショット契約を崩さず段階導入できる。

### 2. 増分Processor

```text
Drive/rcloneで変更を検出
  → 安定したファイル識別子＋内容ハッシュで旧版と新版を特定
  → 変更ファイルだけ解析・正規化
  → 旧版の寄与を除去、新版の寄与を追加
  → 影響する睡眠日・日次Health・睡眠区間Healthを再計算
  → 完全な新スナップショットを原子的に発行
```

影響範囲は次の手順で求める。

1. 旧版と新版が持つ睡眠記録、Health記録、診断の対象範囲の和を取る。
2. 睡眠記録は18時境界で属する睡眠日へ写像する。
3. 30分以内の前後記録をたどり、結合チェーンが切れるまで拡張する。
4. 出典間重複がある場合は、その重複連結成分まで拡張する。
5. 影響した睡眠日は主睡眠・仮眠・補助睡眠の分類を全て再計算する。
6. Health日次集計は影響したローカル日、睡眠区間集計は影響した睡眠ブロックを再計算する。
7. 再計算結果を月別索引へ反映する。旧版だけに存在した月・日からの削除も処理する。

ファイル名だけを識別子にしない。同名更新とDrive上の別ファイルを区別できる安定IDを使い、内容ハッシュが同じ場合だけ解析を省略する。

## 受入ゲートと実施結果

### 正しさ

同一raw一式から、全件再構築と増分再構築を別々に実行し、`generatedAt`、`snapshotId`など実行ごとに変わる項目を除いて論理的に完全一致させる。

必須シナリオ:

- 新規ファイル追加
- 同名ファイルの内容訂正
- ファイル削除相当と復元
- 月末から月初をまたぐ睡眠
- 18時境界をまたぐ睡眠
- 30分結合の直前・途中・直後の訂正
- 複数出典の完全重複・部分重複
- Health指標だけを含む変更
- 変更なしの再実行
- 処理中の異常終了後の再開

比較対象は入力ファイル状態、睡眠記録、ブロック、睡眠日、重複、Health指標、出典要約、診断のID集合・値・件数・ハッシュとする。

### 表示互換性

- トップの最新日、7日比較、30日比較が現行全件ロードと一致する。
- 選択月のraw/unified切替、出典設定、日跨ぎ表示、分割睡眠、印刷が現行全件ロードと一致する。
- 新しいsnapshotId公開後、status検知から該当画面更新までが1ポーリング周期以内である。
- 過去月を表示中に新着が来ても、選択月と画面状態が勝手に変わらない。

### 性能

実機N100で少なくとも次を分けて測る。

- Drive到着からローカルraw公開
- raw公開から完成スナップショット発行
- snapshotId検知から画面反映
- 変更なしポーリングの応答時間・転送量
- 1日分変更時と全件再構築時のCPU時間、壁時計、最大メモリー

目標値はO-15bの暫定目標に合わせ、Drive到着後5分以内を最初の受入値とする。測定値なしで「リアルタイム達成」とは判定しない。

## 実施順序の妥当性

1. **スナップショットキャッシュと軽量status**: 現行仕様を変えず、毎分の重複読込を先に除去できる。
2. **画面別・期間別API**: 転送量とブラウザーの再計算量を減らす。raw/unified互換試験を同時に行う。
3. **変更ファイルキャッシュと増分Processor**: Drive到着後の主要な処理時間を短縮する。完全再構築との一致試験を必須にする。
4. **rcloneによるDrive実機取得**: 取得、Processor、画面の3区間を個別計測し、5分目標を判定する。
5. **定期完全再構築**: 毎回ではなく、手動・夜間の整合性監査と復旧手段として残す。

この順序は低リスクな読取改善から始められる。O-15の鮮度目標の合否は、増分ProcessorとDrive実機取得まで完了して初めて判定できる。

## 最終結論

ユーザー提案の「トップは限定期間、月画面は選択月だけ」は採用できる。トップを7日だけに切り詰めず31睡眠日分の軽量要約を残し、月をProcessorの正しさの境界にせず、期間APIの手前にキャッシュ／索引を置くことが条件である。

この修正を反映した設計とローカル実装はファクトチェック、妥当性チェック、完全一致試験を通過した。O-15全体の合格は、N100実機でDrive到着後5分以内を確認するまで保留する。
